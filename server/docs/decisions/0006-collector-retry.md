# 0006. 수집기 외부 호출 재시도

- 상태: 채택 (2026-11-22)
- 결정자: sychoi
- 관련: [0003 YouTube 수집기](0003-youtube-collector.md), `server/src/youtube-collector/retry.ts`

## 배경

수집기(GitHub Actions)는 YouTube `search.list`·`videos.list`와 서버 `seed-config`·`sync`를 호출한다. 두 HTTP 함수(`youtube.client`의 `get`, `sync.client`의 `call`)에는 15초 타임아웃만 있고 재시도가 없었다. 그래서 일시적인 실패 하나로 다음 손실이 생겼다.

| 호출        | 재시도 전 실패 시 손실                                       |
| ----------- | ------------------------------------------------------------ |
| search.list | 그 검색어로 찾을 후보                                        |
| videos.list | 그 배치(50개)의 재검증·신규 확인. 그날은 추가도 삭제도 안 됨 |
| seed-config | 그날 수집 전체                                               |
| sync        | 그 채널의 그날 결과                                          |

## 결정

### 1. 재시도

HTTP 함수 두 곳에 공통 `withRetry`(`retry.ts`)를 둔다. 호출마다 감싸거나 워크플로 전체를 다시 돌리지 않는다.

| 항목               | 값                                                                                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 최대 시도          | 3회 (첫 시도 + 재시도 2회)                                                                                                                           |
| 대기               | 1초, 2초 + 0~500ms 무작위. `Retry-After`(초)가 있으면 그 값, 최대 10초                                                                               |
| 타임아웃(15초)     | 읽기 요청은 **1번만** 다시 시도한다(`timeoutRetries`)                                                                                                |
| 재시도 안 함(공통) | 400·401·403·404, YouTube 429·할당량 초과, 응답 형식 오류(JSON 아님·zod)                                                                              |
| 검색 예산          | `search.list` 재시도도 한 번의 검색으로 세어 `SEARCH_CALL_BUDGET`·`SEARCH_CALLS_PER_CHANNEL`에서 뺀다. 상한이나 시간 상한에 닿으면 재시도하지 않는다 |
| 로그               | 재시도마다 Actions 로그에 한 줄 (`… 재시도 2/3: <원인>`)                                                                                             |

요청마다 다시 보낼 실패의 범위가 다르다.

| 요청                                       | 다시 보냄                                                                      | 다시 보내지 않음                                     |
| ------------------------------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------- |
| YouTube `search.list`·`videos.list` (읽기) | 연결 실패(`fetch failed`), 본문 수신 중 끊김(`terminated`), 타임아웃(1번), 5xx | 4xx, 429                                             |
| 서버 `seed-config` (읽기)                  | 연결 실패, 본문 수신 중 끊김, 타임아웃(1번), 429, 5xx                          | 4xx                                                  |
| 서버 `sync` (쓰기)                         | 연결 실패(`fetch failed`), 앱이 돌려준 500·503·429                             | 타임아웃, 본문 수신 중 끊김, 프록시(Caddy)의 502·504 |

재시도를 다 써도 실패하면 기존 처리 그대로다. 검색은 그 검색어만 건너뛰고, `videos.list`는 `failedIds`("상태 모름", 삭제 근거로 쓰지 않음), sync는 그 채널만 실패로 보고하고 다음 실행이 다시 처리한다.

성공 응답의 본문은 `readJson`으로 읽는다. JSON 이 아니면 예전처럼 `null`(이후 형식 오류)로 보지만, 본문을 받다가 끊기거나 타임아웃이 나면 오류를 그대로 던져 재시도 판단에 맡긴다. Node 24 fetch(undici)의 오류 모양(`TypeError('fetch failed')`, `TypeError('terminated')`, `DOMException` `TimeoutError`)은 로컬 서버로 확인했다(11.22 리뷰).

### 2. 검색 시간 상한

실행 시작부터 `SEARCH_TIME_LIMIT_SECONDS`(기본 600초)가 지나면 새 검색과 검색 재시도를 멈추고(`stoppedBy: 'time'`, 실패 아님) 동기화로 넘어간다. 워크플로 제한(15분) 안에 동기화할 시간을 5분 남기기 위해서다.

### 3. 할당량 초과 분류와 예약 시각

- YouTube 429(사유와 관계없이)와 `rateLimitExceeded`는 할당량 초과로 본다(`stoppedBy: 'quota'`, 실패 아님). `search.list` 일일 한도('Search Queries per day')가 403 `quotaExceeded`가 아니라 **429 `rateLimitExceeded`**로 왔기 때문이다(11.22 YouTube Collect #3). 이전에는 잘못된 키와 같은 `rejected`로 분류돼 실행이 실패로 끝났다.
- 예약 실행을 05:00 KST(`0 20 * * *`)에서 05:17 KST(`17 20 * * *`)로 옮겼다. 정각은 GitHub 예약 실행이 몰려 지연·누락되기 쉽고, 11.22 05:00 실행이 생성되지 않았다.

## 검색 재시도를 예산에서 빼는 이유

실패한 `search.list` 호출이 할당량(호출당 100 units)을 쓰는지 확인하지 못했다. 쓴다고 보고 세야 일일 한도를 넘지 않는다. 대신 재시도가 생긴 날은 실제 검색 횟수가 그만큼 줄어든다.

## sync 를 다시 보내는 범위를 좁힌 이유

sync 는 같은 요청을 다시 보내도 **개수는 목표로 수렴하지만, 어떤 영상이 축출되는지는 달라질 수 있다.** 그래서 서버가 요청을 처리하지 않았거나 롤백했다고 볼 수 있을 때만 다시 보낸다.

- **이미 커밋된 요청을 다시 보내는 경우**: 한 요청이 새 영상을 넣고 가장 오래된 N개를 축출했는데, 그 N개가 같은 요청 안의 갱신 대상이었다고 하자. 다시 보내면 upsert 가 그 N개를 새 행(새 `createdAt`)으로 다시 넣고, 그다음으로 오래된 N개를 축출한다. `evictedCount`도 재시도분만 보고된다.
- **아직 처리 중인 요청과 겹치는 경우**: 수집기가 15초에 끊어도 서버 트랜잭션은 계속 돌 수 있다. 같은 채널의 sync 두 개가 각자 개수를 세고 같은 영상을 지워 유지 개수를 넘길 수 있다. 워크플로 `concurrency`가 보장하던 "같은 채널 sync 는 한 번에 하나" 전제를 재시도가 깨는 것이다.

타임아웃·`terminated`·프록시 502·504 는 둘 중 하나일 수 있어 다시 보내지 않는다. 앱의 500 은 전역 예외 필터가 트랜잭션 롤백 뒤에 돌려주므로 다시 보낸다.

## 타임아웃 재시도를 1번으로 묶는 이유

타임아웃 한 번이 15초다. 3번 시도하면 호출 하나가 최악 약 48초가 되고, YouTube 가 응답하지 않는 날 재검증(`videos.list`, 채널당 100개 × 9채널 ≈ 18배치)만으로 약 14분이 걸린다. 1번으로 묶으면 호출당 약 31초, 재검증 약 9.5분이다. 연결 실패와 5xx 는 응답이 빨리 오므로 3번을 유지한다.

## 남은 위험 (이번 범위 밖)

- **연결 실패로 보이지만 서버가 받은 sync**: `fetch failed`는 대부분 연결 전 실패지만, 요청을 보낸 뒤 소켓이 끊겨도 날 수 있다. 이때 다시 보내면 위 축출 차이가 생길 수 있다. 완전히 막으려면 서버 sync 에서 축출 전에 채널 행을 잠근다(`SELECT … FOR UPDATE`).
- **재검증 자체의 시간**: 검색 시간 상한은 검색만 멈춘다. YouTube 가 응답하지 않는 날 재검증(약 9.5분)과 서버 sync(채널마다 최대 15초) 합이 약 12분이라 15분 안이지만, 채널이나 보유 개수가 늘면 다시 계산해야 한다.
- **분당 한도 429 도 그날 검색을 멈춘다**: 429 를 모두 할당량 초과로 보므로, 짧은 호출 한도에 걸려도 그날 검색은 멈추고 실행은 성공으로 끝난다. 로그의 `종료 사유: quota`와 `YouTube 할당량 초과로 검색을 중단합니다` 줄로 확인한다.
